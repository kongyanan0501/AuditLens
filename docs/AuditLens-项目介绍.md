# AuditLens AI 项目介绍

> 给业务、管理层和开发一起用的说明。前半讲清「为什么做、谁来用、怎么用」；后半讲清「系统怎么设计、代码怎么改」。  
> 规则与阈值以 [`business-decisions.md`](./business-decisions.md) 为准，表结构以 [`supabase/schema.md`](../supabase/schema.md) 为准，实施进度以 [`todo.md`](../todo.md) 为准。

---

## 1. 三十秒版本

AuditLens AI 是给企业内审和财务合规用的风险工作台。

审计人员上传一份费用或收支流水（Excel / CSV）。系统用固定规则扫完全部记录，标出重复发票、缺审批、金额离群、供应商过于集中，算出 0–100 的风险分，再按公司制度给高风险项写一段可引用条款的说明，并生成可归档的审计报告。发现项可以分派给业务对接人整改，由审计验收后关闭。全过程留下证据、规则版本和操作记录。

一句话原则：**规则判定风险，大模型只负责解释。** 没有配置大模型时，检测、评分和模板报告仍然完整可用。

---

## 2. 要解决的业务痛点

内审面对的往往不是「没有数据」，而是「数据在表里，风险靠人翻」。

| 日常做法 | 实际困难 | AuditLens 对应能力 |
|----------|----------|-------------------|
| 抽几张凭证、凭经验看异常 | 覆盖不稳定，同一批数据不同人结论不同 | 同一套规则扫完全部流水，结果可复现 |
| 发现写在邮件或表格备注里 | 说不清依据哪条制度、哪几行凭证 | 每条发现带规则编号、阈值、凭证快照、制度条款 |
| 整改靠微信催 | 谁接了、交了什么证明、谁验收，事后对不上 | 工单从待复核走到关闭，每一步有人和时间 |
| 报告临时拼 | 换一期就要重写，底稿缺任务号和规则版本 | 报告结构固定，导出带任务号、时间、操作人、规则版本 |
| 把整表丢给聊天机器人 | 结论不稳定，也无法当正式底稿 | 判责留在规则里；模型只解释高风险项，且可降级 |

当前范围是「一批流水的风险发现 + 整改闭环」，不替代总账、费控或完整的内控评价系统。

## 3. 三类人，三种用法

```text
审计人员          看全量任务和问题
    │             确认风险 / 标误报 / 分派 / 验收关闭
    │             调整规则阈值、导出报告
    ▼
业务对接人        只看分派给自己的待办
                  填写整改说明、上传证明，提交验收
                  不能自己把问题关掉

管理层            看仪表盘上的管理层摘要
                  风险分、高风险数量、优先整改的前三项
```

| 角色 | 登录后主要去向 | 能做的事 |
|------|----------------|----------|
| 审计（`auditor`，新用户默认） | 上传、仪表盘、报告、规则设置 | 上传分析、看全部问题、改阈值、分派、验收 |
| 业务（`business`） | 仪表盘「我的待办」 | 处理分给自己的项：提交说明和附件，等待审计验收 |
| 看摘要的人 | 同一套仪表盘 | 看评分、问题分布、优先整改项；不单独做一套管理层系统 |

一个审计任务只指定一名业务对接人。分派时填对方邮箱，对方必须已是业务角色。

## 4. 业务人员怎么用

### 4.1 审计人员：从上传到归档

1. **登录**  
   使用邮箱和密码进入系统。未登录不能打开工作台。

2. **上传流水**  
   打开「上传」，选择 `.xlsx`、`.xls` 或 `.csv`，单文件不超过 5 MB。表头用中文或英文都可以，至少要有：日期、类型（收入/支出）、金额、供应商、发票号。审批人、部门、类别、地区可以有。  
   演示可用仓库里的 `fixtures/demo-financial-audit.csv`，里面故意放了重复发票、缺审批和金额离群。

3. **看总览**  
   分析结束后进入仪表盘：风险分、问题类型分布、管理层摘要（结论、高风险数量、优先整改前三项）、问题列表。

4. **复核一条发现**  
   展开某一行，能看到：
   - 命中了哪条规则、当时用的阈值和规则版本
   - 关联的原始凭证（日期、金额、供应商、发票号、审批人）
   - 若是高风险且已配置模型：为什么可疑、引用了哪条制度、建议怎么改

5. **处理工单**  
   见下一节状态。确认是风险后，在任务上指定业务对接人；对方提交证明后，审计选择通过关闭或驳回。

6. **带走报告**  
   打开该任务的报告，可下载 Markdown、复制全文或打印。导出内容附带任务号、时间、操作人和规则配置版本，便于放进底稿。

### 4.2 业务对接人：只处理自己的项

1. 登录后仪表盘显示「我的待办」，看不到别人的任务全貌。  
2. 阅读审计给出的原因和凭证。  
3. 填写整改措施和完成说明（各至少 10 个字），并上传至少一份附件（截图、PDF，或修正后的流水）。修正文件只作为证明保存，不会自动重跑规则。  
4. 提交后状态变为「待验收」。通过或驳回由审计决定。

### 4.3 一条问题怎么走完

```text
待复核
  ├─ 标为误报 ──────────────► 可直接关闭
  └─ 确认为风险
        └─ 分派给业务对接人 ► 整改中
              └─ 业务提交说明和附件 ► 待验收
                    ├─ 审计通过 ► 已关闭
                    └─ 审计驳回（须写备注）► 回到整改中
```

也可以把未结束的问题重新打开为「待复核」，重新打开时必须填写备注。审计不能从「整改中」直接关掉，必须等业务交验收材料。

每一次状态变化都记在操作轨迹里：谁、何时、从哪一态到哪一态、备注是什么。

## 5. 设计原理

### 5.1 判责和解释分开

| | 规则与统计 | 大模型 |
|--|------------|--------|
| 做什么 | 决定「算不算问题」、严重程度、风险分 | 用制度语言说明「为什么可疑、可以怎么改」 |
| 输入 | 解析后的每一行流水 + 当前生效阈值 | 仅高风险项 + 检索到的制度片段 |
| 失败时 | 解析失败则整单失败并写明原因 | 单条解释失败就跳过该条；整段模型不可用则保留规则原文，报告改用固定模板 |
| 人可以改什么 | 阈值可配置，且只影响之后新跑的任务 | 人仍要确认、误报、分派、验收；模型不关单 |

这样做是为了让同一份表、同一套阈值，今天和明天跑出来的问题清单一致。聊天式回答做不到这一点，也不能单独作为底稿。

### 5.2 证据跟结论走在一起

问题写入数据库时，会把相关原始行抄成快照（`metadata.evidence`），并归档规则编号、版本、阈值、规则初判、模型解释和归档时间（`metadata.workpaper`）。以后即使原文件不在手里，打开这条问题仍能看到当时依据的行。

### 5.3 先闭环，再接日常系统

已经做到：上传 → 检测 → 解释 → 报告 → 分派 → 线上提交证明 → 审计验收。  
尚未做（Phase 12）：从费控或 ERP 自动取数、按期间抽检、高风险解释须人工确认后才写入正式底稿、企微或邮件提醒。  
明确不做：多法人平台、对接完整 GRC、等保整包、同时接很多外部系统。

### 5.4 数据按人和角色隔开

审计看自己权限内的全量；业务只能看到分派给自己的问题。数据库用行级安全策略执行，不靠页面上「藏按钮」alone。模型密钥和向量库密钥只在服务端使用。

## 6. 一次分析里面发生了什么

用户点击「开始分析」后，服务端按固定顺序跑六个步骤。顺序不能随意对调：后面的步骤依赖前面写好的数据。

```text
上传的表格
    │
    ▼
1. 解析        表头对齐、类型和金额归一，得到一行行标准记录
    │          解析失败 → 任务标记失败，后面不再跑
    ▼
2. 规则检查    重复发票、达到金额却没有审批人
    ▼
3. 异常检测    金额相对整表均值过高、单一供应商支出占比过高
    ▼
4. 风险评分    按问题条数从 100 分往下扣，限制在 0–100
    ▼
5. 制度解释    只对「高」严重程度检索制度并生成说明
    │          没有模型或向量库密钥 → 跳过，保留规则原文
    ▼
6. 生成报告    执行摘要、发现项、风险分析、整改建议
    │
    ▼
写入数据库：任务、问题（初始为「待复核」）、报告
页面跳到该任务的仪表盘
```

对应代码入口：`app/api/audit/route.ts` 接收文件并建任务，`server/langgraph.ts` 编排上述六步。

### 6.1 四类发现（给业务讲的版本）

| 业务说法 | 规则编号 | 怎么判定 | 默认严重程度 |
|----------|----------|----------|----------------|
| 同一张发票出现多次 | `R-DUP-001` | 发票号去空格后相同且多于一次；空发票号不参与 | 高 |
| 支出没有审批人 | `R-APR-001` | 支出，且金额达到「必审金额」，审批人为空。收入不查。必审金额默认 0，即所有支出都要有审批人 | 中 |
| 某一笔金额离群 | `R-ANM-001` | 金额大于「全部记录平均值 × 倍数」。默认倍数 5。达到该门槛两倍则为高，否则为中。平均值为 0 时不做这项 | 中或高 |
| 钱过于集中在一个供应商 | `R-VEN-001` | 只统计支出。某一供应商金额占比超过阈值（默认 50%） | 中或高 |

### 6.2 风险分怎么读

```text
分数 = 100
     − 重复发票条数 × 10
     − 异常条数 × 5
     − 审批缺失条数 × 8
```

分数限制在 0 到 100。它表示「这批流水相对这套规则有多干净」，不是信用评级，也不是审计意见本身。仪表盘上的管理层摘要由这个分数和问题列表直接算出来，不再额外调用模型。

审计可以在「规则设置」里调整三个数：金额异常倍数、供应商占比、必审金额。每次发布都要写变更说明，旧版本保留。已经跑完的任务仍使用当时的版本，不会被新阈值改写。

### 6.3 制度解释怎么来

知识库里是本公司制度条目，每条有制度名、条款号和正文（报销、授权、采购等）。系统把高风险项的类型、严重程度和规则说明变成向量，到 Pinecone 里取最相近的 5 条，再让模型按固定结构回答：

- 为什么构成风险  
- 引用了哪条制度（形如 `《制度名》条款号`）  
- 整改建议  

中、低风险保持规则引擎原文，不调用模型，以控制成本和幻觉范围。

## 7. 技术架构

系统是一个 Next.js 应用：页面、接口和审计编排都在同一项目里，没有单独的后端服务。

```text
浏览器
  登录 / 上传 / 仪表盘 / 报告 / 规则设置 / 我的
        │
        ▼
  app/api          鉴权、校验文件、把工作交给 server
        │
        ▼
  server/          解析、规则、异常、评分、检索、报告、工单
        │
        ├── lib/ai-provider.ts    聊天与向量化（OpenAI 或通义）
        ├── lib/pinecone.ts       制度向量检索
        └── Supabase              账号、业务表、行级权限、整改附件
```

依赖只能往下走：

```text
app（页面和 API） → server（审计逻辑） → lib（数据库客户端、模型工厂、向量库）
types（领域类型）被各层使用，自己不引用业务代码
```

页面组件不直接调用模型或向量库。业务节点里也不直接 `new` 某个厂商的 SDK，而是通过工厂按环境变量选择实现。这样换 OpenAI / 通义时，规则和工单不用改。

### 7.1 技术栈

| 层次 | 选用 | 在本项目里的职责 |
|------|------|------------------|
| 应用框架 | Next.js 15（App Router）、React 19、TypeScript | 页面、服务端渲染、API |
| 界面 | Tailwind CSS 4、shadcn/ui | 金融工作台风格的中文界面 |
| 编排 | LangGraph | 六个审计步骤的固定流水线 |
| 模型 | OpenAI（默认）或阿里云百炼通义（`AI_PROVIDER=qwen`） | 高风险解释、可选的报告润色、文本向量 |
| 向量库 | Pinecone | 制度条款检索，默认索引名 `auditlens`，1536 维 |
| 数据与登录 | Supabase（Postgres + Auth） | 用户、任务、问题、报告、规则版本、附件 |
| 表格解析 | SheetJS（`xlsx`） | Excel / CSV → 标准记录 |

本地开发：Node.js 20+，`npm run dev`，地址 `http://localhost:3000`。

### 7.2 主要页面与接口

| 路径 | 谁用 | 作用 |
|------|------|------|
| `/login` | 所有人 | 邮箱密码登录 |
| `/upload` | 审计 | 选择文件并开始分析 |
| `/dashboard` | 审计看全量；业务看待办 | 评分、分布、摘要、问题工作台 |
| `/report/[id]` | 有权查看该任务的人 | 阅读并导出报告 |
| `/settings/rules` | 审计 | 查看和发布规则阈值 |
| `/me` | 所有人 | 当前账号；演示环境可切换角色 |
| `POST /api/audit` | 审计 | 创建任务并跑流水线 |
| `POST /api/tasks/[id]/assign` | 审计 | 为整个任务指定业务对接人 |
| `PATCH /api/issues/[id]` | 按角色 | 推进工单状态 |
| 附件接口 | 业务上传、审计查看 | 整改证明，文件在私有存储桶 |

路由保护在 `middleware.ts`。上传、规则配置在页面和 API 两侧都限制为审计角色。

### 7.3 数据放在哪里

```text
profiles                 角色：auditor 或 business
audit_tasks              一次上传 = 一个任务（文件名、状态、分数、规则版本）
audit_issues             一条发现（类型、严重程度、说明、工单状态、对接人）
audit_issue_events       状态变更轨迹
audit_issue_attachments  整改附件索引（文件在 Storage）
audit_reports            该任务的 Markdown 报告（一个任务一份）
audit_rule_configs       阈值的历史版本，同时只有一条生效
knowledge_base           制度正文（向量在 Pinecone，这里留可检索的原文）
```

任务状态：`pending` → `running` → `completed` 或 `failed`。  
问题一开始都是 `pending_review`（待复核）。

### 7.4 目录怎么读代码

```text
app/           页面与 API，保持薄：校验后调用 server
components/    展示：上传卡片、评分卡、问题工作台、报告
server/        审计引擎（见下表）
lib/           Supabase 客户端、模型工厂、向量库、上传限制、导出
types/         Record、Issue、Task 等共享类型
hooks/         例如登录态
supabase/      SQL 迁移 + schema.md
fixtures/      可复现的演示流水
```

| 文件 | 职责 |
|------|------|
| `server/langgraph.ts` | 六步编排与状态 |
| `server/parse-excel.ts` | 表头别名、类型与金额归一 |
| `server/rules.ts` | 重复发票、审批缺失 |
| `server/anomaly.ts` | 金额离群、供应商集中 |
| `server/audit-engine.ts` | 风险分 |
| `server/rule-config.ts` | 阈值读取与发布 |
| `server/rag.ts` | 检索、提示词、制度种子 |
| `server/report.ts` | 四段式报告与无模型时的模板 |
| `server/audit-repository.ts` | 把结果写入数据库，含证据与底稿快照 |
| `server/issue-workflow.ts` | 谁能把工单推到下一态 |
| `server/profiles.ts` | 角色 |

## 8. 开发步骤与方法

项目按阶段推进，Phase 0–11 已完成，Phase 12（自动取数、抽检、解释确认门闩、通知）尚未开始。做功能时一次只做一个阶段里的一块，避免把「平台化」提前做进来。

### 8.1 从零在本机跑通

```bash
npm install
cp .env.example .env.local
```

`.env.local` 至少填写：

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`

数据库：按 [`docs/supabase-setup.md`](./supabase-setup.md) 建项目、执行 `supabase/migrations/` 里的 SQL、打开邮箱登录，并在 Supabase 里建测试用户。新用户默认为审计角色。

可选，用于制度解释和 AI 报告：

- `AI_PROVIDER=openai` 或 `qwen`
- 对应的 `OPENAI_API_KEY` 或 `DASHSCOPE_API_KEY`
- `PINECONE_API_KEY`（索引默认 `auditlens`，1536 维）

配置好模型与 Pinecone 后执行 `npm run seed:kb`，把制度条目写入向量库和 `knowledge_base`。改了制度正文后需要再跑一次。

```bash
npm run dev
```

登录 → 上传 `fixtures/demo-financial-audit.csv` → 仪表盘看问题和分数 → 打开报告。未配模型时，前四步和模板报告仍然成功，只是没有制度引用。

演示时若需要业务账号视角，设置 `ALLOW_DEMO_ROLE_SWITCH=true` 后，可在「我的」页切换角色。正式环境不要打开这项。

### 8.2 改代码时的顺序

1. 看 [`todo.md`](../todo.md)，确认当前阶段，不提前做下一阶段。  
2. 看 [`PROJECT.md`](../PROJECT.md)，确认要改的模块在哪一层。  
3. 动规则、阈值、评分、解析含义、模型行为或权限时，先读 [`docs/business-decisions.md`](./business-decisions.md)。  
4. 动表、行级策略或索引时，先读 [`supabase/schema.md`](../supabase/schema.md)。  
5. 改完后，同一批改动里同步对应文档（见下）。  
6. 提交前运行 `npm run lint` 和 `npm run build`。和审计计算相关的改动，加上已有测试：

```bash
npm run test:audit      # 规则、异常、评分
npm run test:langgraph  # 流水线
npm run test:rag        # 检索与解释
npm run test:report     # 报告结构
npm run typecheck
```

### 8.3 哪类改动必须改哪份文档

| 你改了什么 | 同一批改动里还要更新 |
|------------|----------------------|
| 阈值、评分公式、列含义、模型解释范围、上传限制、工单规则 | `docs/business-decisions.md`，并在文末变更日志加一行 |
| 表、列、索引、行级安全 | `supabase/migrations/*.sql`、`supabase/schema.md`、`types/database.ts`，必要时 `types/audit.ts` |
| 模块边界或流水线顺序 | `PROJECT.md`，以及 `docs/architecture.md` 的对应摘要 |
| 阶段完成 | `todo.md` 勾选 |

纯样式、不改变行为的重构、依赖升级，不必改业务决策文档。

### 8.4 加一条新规则时建议的落点

1. 在 `types/audit.ts` 增加问题类型（若需要）。  
2. 在 `server/rules.ts` 或 `server/anomaly.ts` 实现判定，返回规则编号、严重程度和可解释的原因。判定必须是纯函数：同样的行和阈值得到同样的结果。  
3. 若有新阈值，放进 `server/rule-config.ts` 和 `audit_rule_configs`，并写迁移。  
4. 确认评分是否把新类型算进去（`server/audit-engine.ts`）。  
5. 高风险才会进 `server/rag.ts`；中低风险保持规则原文。  
6. 用 `server/audit-engine.test.ts` 盖住正例和反例，再更新 `docs/business-decisions.md`。  
7. 不要在 React 组件里写判定逻辑。

### 8.5 换模型厂商

实现 `lib/ai-provider.ts` 里已有的聊天与向量化接口，在工厂里按 `AI_PROVIDER` 注册，并补 `.env.example`。`server/rag.ts` 和报告节点只调用这个接口。向量维度需与 Pinecone 索引一致（当前 1536）。

### 8.6 开发时不要破坏的边界

- `server/` 不引用 `components/`；`lib/` 不引用 `server/`。  
- 浏览器代码不读取 `OPENAI_API_KEY`、`DASHSCOPE_API_KEY`、`PINECONE_API_KEY`。  
- 查询审计数据时带上当前用户，并依赖数据库行级策略，不用用户自填的 metadata 当权限。  
- 流水线节点顺序保持：解析 → 规则 → 异常 → 评分 → 解释 → 报告。  
- 界面文案用中文，代码里的名字用英文。

## 10. 介绍时可以用的结构

面向非技术听众，按这个顺序讲，大约 8–10 分钟：

1. 痛点：翻表、靠邮件整改、报告对不上凭证（第 2 节）。  
2. 产品一句话和原则：规则判风险，模型只解释（第 1 节）。  
3. 现场走一遍：上传演示表 → 仪表盘 → 展开一条高风险 → 指出凭证和制度条款（第 4 节）。  
4. 闭环：确认、分派、业务交证明、审计验收（第 4.3 节）。  
5. 边界：现在靠上传；自动取数和通知是下一步；不做大平台（第 5.3、第 9 节）。

面向开发，在上面之后补：

6. 六步流水线和降级（第 6 节）。  
7. 分层和「密钥只在服务端」（第 7 节）。  
8. 改规则必须同时改 `business-decisions.md`，改表必须同时改 `schema.md`（第 8 节）。

备用问答：

| 问题 | 回答要点 |
|------|----------|
| 模型会不会把正常业务判成风险？ | 判责在规则。人可以标误报。模型不决定关单。 |
| 没配 API Key 能用吗？ | 能完成检测、评分和模板报告。制度引用和 AI 报告会跳过。 |
| 数据和别人串吗？ | 登录后按用户和角色隔离；业务只能看到分给自己的问题。 |
| 阈值改了，旧报告变不变？ | 不变。新阈值只作用于之后新跑的任务，旧任务记下当时的版本。 |
| 和会计软件是什么关系？ | 读已经导出的收支流水，产出风险清单和整改记录，不记账。 |
